# 高危-1：API 边界输入校验 — 修复报告

> 修复方法论文：定位 → 明确范围 → 同类扫描 → 真实调用验证 → 不越界
> 日期：2026-08-18

## 1. 定位（真正的问题是什么）

报告《security-and-bug-review.md》关于"API 边界完全没有输入校验"的描述已**过时**：

- `apps/api/src/main.ts` 早已注册全局 `ValidationPipe`（`whitelist: true, transform: true, forbidNonWhitelisted: false`），上次 remediation 已补。
- 真正残留：所有 `@Query()` 接收裸字符串、`@Body()` 有 1 处行内对象字面量，**运行时零校验**。

但进一步实测发现**更深层根因**，这也是"注册了管道却仍无校验"的真相：

> 项目用 **`tsx`** 运行 API（`apps/api` 的 `start`/`dev`，生产 `infra/docker/api.Dockerfile` 同样是 `tsx src/main.ts`）。`tsx` 基于 esbuild，**不生成 `design:paramtypes` 装饰器元数据**。NestJS `ValidationPipe` 依赖该元数据识别 DTO 类型，缺失时直接跳过校验——**dev / prod / test 三个环境里管道都是空操作**。

实证（`node + @swc-node/register` 下）：
```
Reflect.getMetadata("design:paramtypes", CatalogController.prototype, "list")
// → [Object, Object, ListCatalogQueryDto]  ✅ 元数据存在，管道可校验
```
而 `tsx` 下该值为 `undefined` → 管道跳过。

## 2. 修改范围（不越界）

| 类别 | 动作 | 范围 |
| --- | --- | --- |
| 输入 DTO | 新增 `pagination.dto.ts`；为 8 个 controller 的 query 补 DTO；1 处行内 `@Body` 改 DTO | catalog / application / demand / feedback / interaction / identity / security / analytics + unified-upload |
| 运行时 | `start`/`dev` 由 `tsx` 改为 swc 加载器；新增 `.swcrc` | `apps/api` |
| 依赖 | `@swc-node/register`/`@swc/core` 移到 `dependencies` | `apps/api` |
| 校验约束 | 字符串长度用 `@MaxLength`（非 `@Max`） | DTO 文件 |
| 不动 | `@Param`、已校验的 `@Body`、main.ts 的管道配置 | — |

**同类扫描**：全仓 14 个 controller 的 `@Query`（约 40+ 处）、行内 `@Body`（1 处）已枚举，未校验输入集中于上述 DTO 缺失处。

**已知残留（不在本次范围）**：`@Param` 的枚举仅做 TypeScript 类型断言，运行时无 class-validator 约束；下游有存在性/归属校验兜底，记为后续项。

## 3. 关键改动清单

- `packages/server/src/system/http/pagination.dto.ts`（新增）：`PaginationQueryDto`（`page`/`pageSize` 数值范围 1–200）。
- 各模块 `*.dto.ts`：新增 `ListXxxQueryDto`（继承分页基类，约束 `sort` 枚举、`status/mode/channel` 枚举、`keyword/query/categoryId/...` 长度上限）。
- `packages/server/src/application/unified-upload.controller.ts`：行内 `{ signature?: string }` → `CompleteUnifiedUploadBodyDto`。
- `apps/api/package.json`：`start`/`dev` → `node --import @swc-node/register/esm-register src/main.ts`；新增 `test:input-validation`。
- `apps/api/.swcrc`：swc 开启 `legacyDecorator` + `decoratorMetadata`。
- `apps/api/vitest.config.ts`：默认套件排除 `test/input-validation.e2e-spec.ts`（避免默认 esbuild 剥元数据导致该 e2e 误失败）。

## 4. 验证（真实测试，非仅类型检查）

| 测试 | 命令 | 结果 |
| --- | --- | --- |
| 单元测试（DTO 约束） | `pnpm --filter @ai-hub/server exec vitest run src/system/http/input-validation.spec.ts` | **13 / 13 通过**（真实 `class-validator.validate()` 断言拒绝非法枚举/范围/超长字符串） |
| 集成 e2e（真实管道+控制器） | `pnpm --filter @ai-hub/api exec vitest run --config vitest.input-validation.config.ts` | **8 / 8 通过**（非法 `sort`/`pageSize`/`status`/`scope` → 400；合法 → 200） |
| 生产命令启动 | `pnpm --filter @ai-hub/api start` | **启动成功**（`Nest application successfully started`，全部路由映射完成） |
| 类型检查 | `tsc --noEmit`（server 改动文件） | 零报错 |

> e2e 使用 swc 转译（`unplugin-swc` + `decoratorMetadata:true`）才能让 `ValidationPipe` 真正生效；默认 esbuild 配置下管道会跳过校验。

## 5. 结论

高危-1 现已**端到端修复**：既补齐了缺失的输入 DTO 绑定，又修掉了"tsx 剥装饰器元数据导致管道空操作"这一根因。开发、生产、测试环境现在都会对 API 边界输入做真实校验。

## 6. 后续建议

- 清理调查中安装但未使用的 `ts-node`/`ts-node-dev`（最终采用 `@swc-node/register`）。
- 将 `test:input-validation` 接入 CI，作为"输入校验不可回归"的门禁。
- 评估 `@Param` 枚举是否也需补 DTO 约束。
