## 二、逐项结论

### 中危-5：HttpException.detail 原样回显（反射型 XSS / 信息泄露）— ✅ 已修

**定位**
- `packages/server/src/system/http/problem-details.filter.ts` 把 `exception.message` 当作 `detail` 原样回显到 JSON 响应体。
- JSON 本身不执行脚本，但若前端误将 `detail`/错误消息当 HTML 渲染（如直接 `innerHTML` 注入告警条），即构成反射型 XSS；同时会泄露内部异常原文。

**修复**
- 新增 `escapeHtml()`，对 `detail` 做 HTML 实体转义（`< > & " '`）后再回显。
- 新增 `SAFE_DOMAIN_CODE` 正则校验 `code` 字段，避免非预期状态码。
- 回显逻辑改为 `message = safeDetail ?? details.title`（无 detail 时回落固定 title，不泄露原文）。

**验证（真实载荷，非仅类型检查）**
- 新增 `packages/server/src/system/http/problem-details.filter.spec.ts` **6/6**：`<script>`/`<img onerror>`/`javascript:` 被转义、常量 detail 原样透传、无 detail 回落固定 title、字符串响应体同样转义。

### 中危-4：SSRF 防护死代码（外部抓取点未接入）— ✅ 已修

**定位**
- 既有 `assertPublicHttpTarget`（`packages/server/src/system/security/ssrf-policy.ts`）提供 DNS 重绑定二次校验、拒绝私有/链路本地/云元数据目标。
- `packages/server/src/identity/dingtalk-api.client.ts` 抓取钉钉 OAuth / 用户信息两个端点**从未调用**该校验，防护形同死代码——攻击者若可控配置即可触发对内网/元数据服务的 SSRF。

**修复**
- 导入 `assertPublicHttpTarget`。
- 新增 `validatedTargets: Map<string, Promise<URL>>` 缓存 + `assertTarget()` 私有方法（校验失败清缓存以便重试）。
- 两处 `fetch` 改为先 `await this.assertTarget(url)` 再 `target.toString()` 出站。

**验证（真实调用，非仅类型检查）**
- 新增 `packages/server/src/identity/dingtalk-api.client.spec.ts` **4/4**：mock `assertPublicHttpTarget` 避免真实 DNS，验证两端点均经 SSRF 校验、拒绝时**不出站**。

### 中危-6：重放 nonce 未绑定真实用户 — ❌ 未改动（需架构决策）

**定位**
- `packages/server/src/system/security/production.middleware.ts:73` 硬编码 `actorEmployeeId: "authenticated-request"`。
- `production.middleware.test.ts:41` 明确断言 `capturedActor === "authenticated-request"`。

**判定**
- 该中间件经 `app.use()` 注册，**执行顺序早于** NestJS 鉴权守卫，此时尚未完成鉴权，拿不到真实 actor。
- 若改为读取 `x-employee-id` 等请求头来"绑定真实用户"，攻击者可直接伪造该头，反而引入更严重的身份伪造漏洞。
- 正确做法是在鉴权之后（守卫 / 拦截器层）绑定真实用户，属架构级改动，超出本次安全改造范围。
- **结论**：标注「需架构决策」，未做不安全改动。

### 低危-6/7：Outbox 幂等键随机化 → 唯一索引去重失效 — ✅ 已修

**定位（真实活 bug）**
- 服务端 `emitOutbox` 用 `randomUUID()` 生成幂等键，且插入缺 `ON CONFLICT DO NOTHING`。
- 下游 `outbox_events_idempotency_key_unique` 唯一索引**永不命中**（每次键都不同），重试 / 重复投递会在 outbox 写入重复事件，进而触发重复下游副作用（重复通知、重复计数修正等）。

**修复**
- **基础层**（4 个 repository 实现均改）：
  - 接口签名加 `idempotencyKey?: string`：`application.types.ts:344`、`feedback.types.ts:59`、`demand.types.ts:294`、`interaction.types.ts:98`。
  - 实现改用 `input.idempotencyKey ?? 兜底键`，并补 `.onConflict((oc) => oc.column("idempotency_key").doNothing())`：
    - `application.repository.ts:1134`
    - `feedback.repository.ts:122`
    - `demand.repository.ts:1173`
    - `interaction.repository.ts:294`
- **调用点接线**（5 个关键业务事件带稳定业务键，使重试去重生效）：
  - `feedback.service.ts:49` → `feedback-created:${record.feedbackId}`
  - `feedback.service.ts:138` → `feedback-status-updated:${input.feedbackId}:${input.status}`
  - `demand.service.ts:1132` → `demand-comment-created:${comment.commentId}`
  - `demand.service.ts:1197` → `demand-report-created:${report.reportId}`
  - `demand.service.ts:1250` → `demand-report-resolved:${report.reportId}`

**验证（真实调用，非仅类型检查）**
- server 包 `tsc` 全量 0 错。
- `feedback.service.test.ts`(9) + `demand.service.test.ts`(20) = **29 例无回归**。
- 新增 demand 测试断言：捕获 `emitOutbox` 入参，验证 `idempotencyKey` 含实体 ID（如 `comment-1`），证明稳定键生效。
