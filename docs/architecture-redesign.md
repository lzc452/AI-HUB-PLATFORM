## 0. 文档目的

本文在 V1 模块化单体已经落地、九条业务流程已固化并重新绘制的基础上，从架构师视角：

1. 系统梳理 **当前架构形态与约束**；
2. 识别 **规模化与可维护性层面的关键风险**；
3. 确立 **分层与上下文映射（C4 视角）** 的目标结构；
4. 给出 **V1 → V2 → V3 的演进路线与门禁**；
5. 提出 **3–5 年长期发展规划** 与 **待补充的架构决策（ADR）**。

所有结论均锚定既有 ADR 与当前仓库结构，不做脱离约束的空想设计。

## 1. 现状梳理（Current State）

### 1.1 代码仓库与运行时形态

- **pnpm monorepo**，统一依赖与构建编排（turbo）。
- 三个可部署应用：
  - `apps/web`：React SPA（前端，端口 8080 经 nginx 反代）；
  - `apps/api`：NestJS **模块化单体**（承载全部领域服务）；
  - `apps/worker`：NestJS **Outbox Worker**（轮询 `outbox` 表，驱动异步副作用）。
- 共享包（packages）：`config` / `contracts` / `database`（Kysely）/`server` / `testing` / `ui` 等，保证契约与基础设施一致。

### 1.2 领域模块全景（9 域）

| 领域 | 职责 |
| --- | --- |
| identity | 认证 / 组织 / RBAC |
| application | 应用草稿、版本、上下架、审核 |
| catalog | 应用 / 市场目录与检索 |
| interaction | 创作者与互动（点赞 / 评价 / 举报） |
| notification | 通知与触达 |
| creator | 创作者侧能力 |
| demand | 创新需求闭环 |
| analytics | 行为聚合与看板 |
| system | 系统级（权限、配置、运维入口） |

### 1.3 基础设施拓扑

- **PostgreSQL 18.4**：主数据存储 + Outbox 事件表。
- **Garage（S3 兼容）**：对象存储（附件上传、短期授权下载）。
- **ClamAV**：文件病毒扫描（仅文件维度）。
- **Prometheus**：指标采集；nginx 反代 + TLS。
- **双机 Docker Compose**：应用与数据双副本部署，无编排平台。

### 1.4 已确立的架构决策（ADR）

- **ADR 0001**：React SPA + NestJS 模块化单体（前端/后端职责分离，后端以模块边界替代早期微服务）。
- **ADR 0002**：PostgreSQL 事务性 Outbox（写业务与写事件同事务，Worker 保证至少一次投递）。
- **ADR 0003**：Garage 对象存储（自建 S3 兼容，规避公有云锁定）。

### 1.5 运行约束（不可逾越的基线）

- 企业内网，安全合规优先于弹性；
- 单实例运行、**无 `tenant_id`**（逻辑隔离未建模）；
- 双机 Docker Compose，无 K8s / 无自动弹性；
- 交付走 GitHub Actions（GHCR 不可变镜像 + SBOM + 供应链证明）。

## 2. 关键问题与风险

| 类别 | 问题 | 影响 | 触发演进阶段 |
| --- | --- | --- | --- |
| 耦合 | 模块化单体模块间隐式依赖（共享 DB 表、跨模块直接调用） | 修改放大、团队踩踏、认知负载高 | V2 |
| 规模化 | 单实例无多租户，数据模型未预留隔离维度 | 无法支撑集团多 BU / 多子公司隔离 | V3 |
| 可用性 | 双机 Compose 无自动故障转移与弹性 | 单机宕机需人工介入，峰值受限 | V2/V3 |
| 可观测性 | 指标有采集但缺乏统一 Trace / 日志关联 | 跨模块排障慢 | V2 |
| 数据治理 | 行为数据聚合与导出权限边界依赖人工规则 | 合规审计成本高 | V2 |
| 安全 | ClamAV 仅覆盖文件，缺运行时与依赖供应链纵深防御 | 攻击面扩大 | 持续 |
| 呈现（已修复） | 流程图元素重叠 / 字体溢出 / 箭头方向错乱 / 节点连线模糊 | 文档可读性差、误导理解 | 本次重绘已解决 |

> 说明：本章所列"呈现问题"已在本次 `docs/flowchart/` 重绘中通过数据驱动绘图引擎（自动折行、容差锚点、2x 高清导出）彻底修复，详见 §6 与工具脚本。

## 3. 目标架构原则

1. **演进式架构（Evolutionary）**：以模块化单体为起点，按门禁逐步抽取边界，不提前微服务化。
2. **模块即边界（Module = Bounded Context）**：每个领域模块对外仅暴露契约（`contracts` 包），禁止跨模块直连私有表。
3. **一切副作用异步化**：写路径只落库 + Outbox，跨域影响交由 Worker / 事件消费，保证主链路简单可预测。
4. **可观测优先**：Metrics / Trace / Log 关联 ID 贯穿 nginx → api → worker → 存储。
5. **安全纵深**：文件扫描 + 依赖 SBOM + 最小权限 + 审计留痕，合规内建而非后置。
6. **约束尊重**：演进不脱离"内网 / 单实例基线 / 双机 Compose"，在不引入 K8s 的前提下提升韧性。

## 4. 分层与上下文映射（C4 视角）

参考 `00-architecture-redesign` 图，目标结构分为五层 + 一个演进层：

```
接入层        u1 企业员工(浏览器) ──HTTPS── nginx(TLS + 反代) ── HTTP/JSON ──▶ 应用层
            ext 外部系统(钉钉 / Dify) ── OAuth / 通讯录 / 通知 / Dify ─────────┘

应用层（NestJS 模块化单体 · V1）  [app 容器]
   identity · catalog · interaction · demand · system · analytics · notification · creator

异步与集成层      worker(Outbox 轮询) ──▶ integ(扫描/通知/导出)

数据层            pg(PostgreSQL + Outbox) · storage(Garage S3)

基础设施层        obs(Prometheus 监控) · cicd(GitHub Actions + 不可变镜像) · ops(备份/降级)

演进层（路线图）  v1 当前形态(单体) ──门禁──▶ v2 边界抽取 ──门禁──▶ v3 平台化多租户
```

- **容器（app）** 仅作逻辑分组可视化，运行时仍是单进程单体；边界在 V2 才逐步物理化。
- **门禁（来自 00 图 e12 / e13）**：
  - V1→V2 门禁：*边界清晰（模块契约稳定）* 且 *团队自治（模块有 Owner）*；
  - V2→V3 门禁：*多租户需求明确（业务侧出现隔离诉求）*。

## 5. 演进路线 V1 → V2 → V3

### V1 · 单体稳固（当前）
- 目标：业务闭环跑通、质量门禁稳定、**模块边界在代码层面可见**（目录 + `contracts`）。
- 退出条件：九条核心流程稳定、监控/CI 闭环、无跨模块私有表直连。

### V2 · 边界抽取
- 目标：将高变化 / 高负载模块（如 `analytics`、`interaction`、`notification`）抽为**独立部署单元**（仍可用同仓库、同 DB 的逻辑服务，或进程内隔离 + 明确 RPC）；引入统一 Trace 与事件总线；双机韧性增强（健康探针 + 优雅下线）。
- 关键动作：
  - 模块契约冻结，跨模块仅经 `contracts`；
  - 事件消费规范化（Outbox → 内部事件总线 → 各订阅方）；
  - 可观测三件套打通（Trace ID 串联）。

### V3 · 平台化多租户
- 目标：在数据模型与基础设施层面引入**租户隔离维度**，支撑集团多 BU / 子公司；对象存储与计算按需弹性；形成内部开发生态（Creator / 应用市场）。
- 前置条件：V2 边界稳定 + 明确的多租户业务诉求。
- 风险对冲：多租户是重大变更，需单独 ADR（数据隔离策略、迁移路径、合规审计）。

## 6. 核心业务流程梳理（九条）

本次重绘使用统一数据驱动引擎，修复了原始图的 **元素重叠、字体溢出、箭头方向错乱、节点连线模糊** 四类问题，并新增 `00` 整体架构图。各流程要点：

| 图 | 流程 | 关键节点 / 决策 |
| --- | --- | --- |
| 01 | 系统架构总览 | Web → nginx → NestJS 单体 → PG / Garage；Worker、监控、CI/CD、生产环境 |
| 02 | 认证与组织 | 账密 / 钉钉 OAuth → 首次绑定注册 → 会话 → 组织同步 → RBAC 统一鉴权 |
| 03 | 应用发布审核闭环 | 草稿 → 自动校验 → 人工审核池 → 上架 / 驳回 / 撤回；版本不可变、上下架与删除保护 |
| 04 | 创新需求闭环 | 提交 → 轻量审核 → 认领 → 方案验证 → 试点 → 转化应用 / 关闭 / 合并 |
| 05 | 市场与互动治理 | 受众权限过滤 → 列表/搜索 → 详情/交付入口 → 点赞评价 → 举报隐藏与审计 |
| 06 | 数据看板与导出 | 行为采集 → 日聚合 → 固定看板 → 权限控制导出 → Dify 最小化问答 |
| 07 | V1 实施路线图 | 8 阶段、门禁、M1–M9 里程碑、全局约束 |
| 08 | 部署与运维 | 双机拓扑、CI/CD 发布、备份恢复、监控告警、故障降级 |
| 09 | 数据流转闭环 | 登录 → 上传 → 审核（通过/修改重审/驳回）→ 上架 → 发现/查看/互动 → 应用（下载/跳转/扫码）→ 聚合反哺 |

**修复手段（工程化沉淀）**：
- 自动折行算法（CJK/ASCII 宽度测量 + `fitNode` 自适应字号与高度）→ 解决字体溢出；
- 容差锚点 `borderAnchor(tol=2)` 替代严格坐标相等 → 解决箭头方向错乱；
- SVG `stroke-width=2` + 箭头 marker 尺寸 10 + 深色 `#3c4a5e` → 解决连线模糊；
- PNG 经 `export-png.mjs` 以 **2x** 由 resvg 导出 → 解决位图模糊；
- 几何校验 `--check`（重叠 / 越界 / waypoint 穿节点）→ 防止回归。

## 7. 长期发展规划（3–5 年）

1. **第一年（稳固 + 边界）**：V1 质量门禁闭环；完成 V2 模块契约冻结与高热点模块隔离；可观测三件套落地。
2. **第二年（韧性 + 数据治理）**：双机韧性增强（探针 / 优雅下线 / 故障演练）；数据治理与导出合规自动化；事件总线规范化。
3. **第三年（平台化）**：若业务出现隔离诉求，启动 V3 多租户（独立 ADR）；对象存储与计算按需弹性评估（仍尊重无 K8s 基线，优先双机增强或轻量编排）。
4. **持续项**：供应链安全（SBOM / 依赖审计）、合规审计自动化、Creator 生态与内部应用市场成熟。
