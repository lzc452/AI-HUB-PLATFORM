## 1. 核心目标

一句话需求：在 AI-HUB-PLATFORM 中新增「本地 vLLM 大模型 API Key 管理」能力——每个登录用户可自助创建、管理 OpenAI 兼容 API Key，经统一网关调用本地部署的 vLLM 模型服务，具备调用鉴权、配额管控与全量用量监控。

| 编号 | 目标 | 衡量口径（设计目标值） |
| --- | --- | --- |
| G-01 自助开通 | 登录用户在控制台自助创建 Key | ≤3 次点击完成创建；明文仅在创建成功时展示一次，之后不可再取 |
| G-02 接口兼容 | 对外完全兼容 OpenAI 格式 | 暴露 `/v1/models`、`/v1/chat/completions`、`/v1/embeddings`；官方 OpenAI SDK 仅改 `base_url` 与 `api_key` 即可调用，含 streaming |
| G-03 安全可控 | Key 全生命周期可管控 | 支持启用/禁用/轮换/删除；禁用与越权调用 100% 返回 401/403；Key 哈希存储，库表泄露不暴露明文 |
| G-04 配额管控 | 限流与配额生效 | 按 Key 维度 RPM/TPM 限流 + 按用户维度日 token 配额；超限返回 429 且带 `Retry-After` |
| G-05 用量可视 | 调用全量可观测 | 100% 调用记录（用户/Key/模型/token/耗时/状态码）；控制台展示今日、近 7 日、近 30 日用量与调用明细 |

### 本期范围

包含：

- 前端（Console 新增「模型服务」模块）：Key 生成、列表查看、禁用/启用、轮换、删除、用量可视化（图表 + 明细表）
- 后端：Key 生命周期管理、Bearer Token 鉴权、OpenAI 兼容请求转发、限流与配额、调用记录与聚合
- 模型服务层：统一网关（OpenAI 兼容路由、调用鉴权、限流熔断、Prometheus 指标与调用统计）
- 部署：compose 新增 vLLM 服务定义（GPU 服务器）

不包含（记入后续版本池，本期不做）：

- 计费与扣费（资金类需求；如后续引入，须先补幂等、对账、资损监控三件套）
- 多租户/组织级数据隔离、跨企业共享
- 多模型源混合路由（接入外部厂商模型）
- vLLM 多机调度、模型微调与量化管理

### 关键假设（可推翻，请确认）

| 编号 | 假设 | 不成立时的影响 |
| --- | --- | --- |
| A1 | 复用平台现有登录态与员工体系，API Key 绑定登录用户，`employee` 角色即可开通 | 需增加独立开通审批或角色白名单 |
| A2 | vLLM 部署于公司 GPU 服务器，对外暴露 OpenAI 兼容 HTTP 端口（默认 8000） | 网关目标地址与部署编排需调整 |
| A3 | 配额为「限流 + 软限额」语义，超额拒绝并提示，不涉及扣费 | 涉及资金则需补齐资金安全三件套 |
| A4 | 单体单实例部署（当前架构为模块化单体，Compose 中无 Redis） | 多实例部署时限流计数器需迁移至 Redis 等共享存储 |

## 2. 技术方案对比

| 维度 | 方案 A：应用层网关（NestJS 模块） | 方案 B：独立 LLM 网关服务 | 方案 C：Nginx/OpenResty + Lua |
| --- | --- | --- | --- |
| 思路 | 在 `packages/server` 新增 `llm-gateway` 模块：Bearer 鉴权 → 限流配额 → 转发 vLLM → Outbox 异步记账 | 独立服务/容器专责路由、鉴权、限流、监控；NestJS 只管 Key 管理与控制台，状态经缓存/心跳同步 | Nginx 承载鉴权限流转发，Lua 脚本实现 Key 校验 |
| 实现成本 | 低：复用现有鉴权、Kysely、Outbox worker、Prometheus | 高：双服务运维、Key 状态同步、二次开发与合规审查成本 | 中：Nginx 部署简单，但 Lua 业务逻辑开发调试成本高 |
| 用户体验 | 中：与业务 API 同进程，高并发 streaming 时有资源争抢 | 好：streaming 友好，可独立扩缩，故障隔离 | 中：功能迭代受 Lua 限制 |
| 风险 | 中：vLLM 慢响应/挂起可能拖累 API 进程，需超时 + 熔断 + 连接池隔离 | 中：架构复杂度与 Key 状态一致性风险 | 高：用量落库、配额、错误映射在 Lua 中难以维护 |
| 上线时间 | 快 | 慢 | 中 |
| 推荐度 | **推荐（本期起步）** | 备选（演进方向） | 不推荐 |

**推荐结论**：方案 A 起步。对外契约与内部结构按「网关抽象」设计——转发适配器（vllm-adapter）、配额拦截器、用量记录端口相互独立；当出现以下任一演进触发条件时，将网关模块平移为方案 B 的独立服务，控制台与对外 API 契约不变：

- 网关转发 P95 延迟 > 500ms 且持续 1 周
- API 进程 CPU 持续 > 70% 达 1 周
- 峰值 QPS > 50，或多实例部署成为硬需求

## 3. 关键风险

| 编号 | 风险 | 类别 | 概率 | 影响 | 等级 | 应对措施 |
| --- | --- | --- | --- | --- | --- | --- |
| RK-01 | Key 明文仅展示一次，用户丢失后无法找回；存储层泄露将导致批量 Key 失效 | 安全 | 3 | 5 | 15 高 | HMAC-SHA256 哈希存储；仅创建时返回明文；支持轮换与管理员批量禁用；泄露应急流程写入 PRD |
| RK-02 | 网关与业务 API 同进程，vLLM 慢响应或挂起拖垮平台 API | 技术 | 3 | 5 | 15 高 | 独立 HTTP agent 与连接池；首 token 超时 30s、整体超时 120s；连续失败熔断；预留拆独立服务路径 |
| RK-03 | vLLM 原生错误（上下文超限、模型不存在、显存不足）直接透传，用户难以理解 | 体验 | 4 | 3 | 12 中 | 统一映射为 OpenAI 兼容 error 结构，message 附中文可读说明 |
| RK-04 | 配额口径不清导致误杀正常调用或超卖 | 数据 | 3 | 3 | 9 中 | 口径写死：RPM/TPM 按 Key 滑动窗口计数，日 token 按用户累计；超限行为（拒绝/提示）明确 |
| RK-05 | 同步写用量记录影响转发延迟 | 技术 | 3 | 3 | 9 中 | 调用记录走 Outbox 异步落库；看板读预聚合表 |
| RK-06 | 需求范围蔓延至计费、多租户、多模型源 | 需求 | 4 | 3 | 12 中 | 本期显式不做；变更走需求变更评估表，记入后续版本池 |
| RK-07 | 缺少监控导致 Key 滥用、异常调用无法及时发现 | 运营 | 3 | 4 | 12 中 | 100% 调用记录；异常告警（单 Key QPS 突增、错误率 > 20%、日配额即将耗尽） |
