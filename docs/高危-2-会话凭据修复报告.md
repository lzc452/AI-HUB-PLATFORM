# 高危-2 修复报告：前端会话凭据存储与 XSS 劫持

> 修复日期：2026-08-18
> 方法论：先定位、明确范围、不越界、同类扫描、真实调用验证

## 一、定位（报告已过时，但缺一环）

报告原描述："`session.store.ts:14,43` 将 `employeeId + sessionId` 写入 `localStorage`；`auth.client.ts` 读取并重放为 `x-session-id`/`x-employee-id` 头。"

经实证核查，**当前代码与报告描述已不同**：

1. **前端不再把凭据写入 localStorage**
   - `apps/web/src/modules/auth/session.store.ts` 仅持久化非敏感的 `employeeId`（注释明确："会话令牌 sessionId 仅存于后端下发的 HttpOnly Cookie 中，绝不在前端可读取的 localStorage 中持久化"）。`employeeId` 仅用于刷新页面时提供"可能已登录"的 loading 提示，最终以服务端 `/actor` 为准。
   - `apps/web/src/shared/api/client.ts` 已改为：身份令牌由后端 **HttpOnly Cookie**（`aihub_sid`/`aihub_eid`）携带，同源自动发送；前端**不再注入** `x-session-id`/`x-employee-id` 请求头（注释："避免 XSS 通过 JS 窃取会话"）。
   - 前端 `document.cookie` 仅读取 `csrf_token`（double-submit CSRF 模式，必须 JS 可读），**不读取会话凭据**。`localStorage` 另仅存侧边栏折叠 UI 偏好，`sessionStorage` 仅存"最近查看的应用 id"——均非凭据。

2. **后端优先读 HttpOnly Cookie**
   - `packages/server/src/authorization/permission.guard.ts:48-51`：优先 `cookies["aihub_sid"]`，请求头仅作非浏览器/测试客户端兼容通道。

3. **真正的残留缺口：会话 Cookie 缺 `Secure` 标志**
   - `packages/server/src/identity/identity.controller.ts` 的 `sessionCookieHeaders` 当前为：
     ```
     Path=/; HttpOnly; SameSite=Lax
     ```
   - 有 `HttpOnly`（XSS 无法读）+ `SameSite=Lax`（缓解 CSRF），但**缺 `Secure`**。这正是报告推荐修复"HttpOnly + **Secure** + SameSite"里缺失的一环（源码注释亦承认"生产走 https 时建议通过配置补 Secure"）。
   - 缺 `Secure` 的风险：攻击者诱导浏览器向 `http://<host>/...` 发起明文请求时，浏览器会连同会话 Cookie 一并发送（降级），在明文链路上可被中间人截获。

**结论**：HIGH-2 的"凭据存 localStorage"存储层已被前置修复；本次真正要补的是会话 Cookie 的 `Secure` 标志，以完整闭合"防 XSS 劫持 + 防明文降级"的防护。

## 二、范围（明确边界，不越界）

- **修**：会话 Cookie 的 `Secure` 标志决策与属性构造（与报告推荐修复一致）。
- **不修**：
  - 前端存储逻辑（已正确，不改动）；
  - 后端 `permission.guard.ts` 的 `x-session-id`/`x-employee-id` 请求头兼容通道（非浏览器/测试客户端需要，不削弱浏览器 XSS 防护，移除会破坏 e2e 测试）；
  - `SameSite=Lax` 维持（合适默认值）；
  - 与 HIGH-2 无关的其它安全项（富文本净化=XSS-3、SSRF、重放 nonce 等）不在本次范围。

## 三、改动

### 1. 新增纯函数模块（便于直接单测，不扩大改动面）
`packages/server/src/identity/session-cookie.ts`：
- `buildSessionCookieAttributes(secure: boolean): string` —— 构造 `Path=/; HttpOnly; SameSite=Lax[; Secure]`。
- `shouldSecureSessionCookie(): boolean` —— `AIHUB_SESSION_COOKIE_SECURE=true|false` 显式覆盖优先；缺省仅 `NODE_ENV==="production"` 开启，开发/测试保持可用（本地 http 不卡登录）。

### 2. 改造 `identity.controller.ts`
- 导入上述纯函数；`sessionCookieHeaders` 改用 `buildSessionCookieAttributes(shouldSecureSessionCookie())` 生成 `flags`，`aihub_sid` 与 `aihub_eid` 均应用该 `flags`。
- `clearSessionCookies`（登出清 Cookie，`Max-Age=0`）无需 `Secure`，保持不变。

## 四、同类问题扫描

- 前端凭据暴露点：已确认无。除非敏感 `employeeId` 外，会话凭据仅存在于后端 HttpOnly Cookie，JS 不可读。
- 后端其它 Cookie：`dingtalk_*` SSO Cookie 已自带 `HttpOnly; Secure; SameSite=Lax`；仅主会话 Cookie 此前缺 `Secure`，本次补齐。

## 五、验证（真实调用，非仅类型检查）

1. **单元 + 控制器级集成单测** `packages/server/src/identity/session-cookie.spec.ts` —— **8/8 通过**
   - 纯函数：`buildSessionCookieAttributes(false)` 含 `HttpOnly`/`SameSite=Lax` 不含 `Secure`；`(true)` 含 `Secure`。
   - `shouldSecureSessionCookie()`：开发/测试默认 `false`；`NODE_ENV=production` → `true`；显式 `AIHUB_SESSION_COOKIE_SECURE=false`（即使生产）→ `false`；`=true`（即使非生产）→ `true`。
   - **真实代码路径**：直接实例化 `IdentityController` 调用其真实的 `sessionCookieHeaders`，断言非生产产出 `aihub_sid=...; ...HttpOnly; SameSite=Lax`（无 Secure），生产产出含 `Secure`，且 `aihub_eid` 同样带 `HttpOnly`。
2. **类型检查**：服务端 `tsc --noEmit` 对改动文件（`identity.controller.ts`、`session-cookie.ts`）零报错。
3. **回归**：既有 `apps/api/test/identity.e2e-spec.ts` **1/1** 通过（测试环境默认 `NODE_ENV=test`，无 Secure，行为不变）。

## 六、部署注意

- 生产（`NODE_ENV=production`，走 https）会自动为会话 Cookie 加 `Secure`；若生产反向代理前终止 TLS 且浏览器直接以 http 访问应用，可显式设置环境变量 `AIHUB_SESSION_COOKIE_SECURE=false` 关闭（不推荐）。
- 如需强制开启（例如非 production 的预发环境走 https），设 `AIHUB_SESSION_COOKIE_SECURE=true`。
